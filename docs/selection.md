# 精選與校準

## 一條資料怎麼變成精選

1. **收進來**：同一網址、同一內容只留一份。普通文章只有標題或摘要時，按信源規則補取正文；影片播放頁使用已提供的文字材料，不把播放器頁面當正文。沒有可信釋出時間的資料先不公開，讀到原文日期後再判斷新舊（見 [信源](sources.md#規則舊文不刷屏) 的“舊文不刷屏”）。
2. **預篩**（`prefilter.md`）：這是不是本行業的事。寬進，只攔明顯無關的：`BLOCK` 的資料不出現在任何公開頁面；`PASS` 和拿不準的 `UNKNOWN` 繼續往下走。只有標題、沒有正文、訂閱摘要或帖子文字的普通文章先等待材料，不評分、不憑標題寫文案，也不進入公開池；材料補齊產生新修訂後再判斷。可展示的空文字或純連結原帖沿用原有評分與原樣展示規則。
3. **評分**（`selection-score.md`）：同一份評分標準獨立打兩次分（0–100）。**兩次之和 ≥ 2 × 門檻**就夠分，門檻按信源分級不同，信源類別還能把某些官方信源的門檻抬高；夠分的還要過第 6 步的去重才進精選。頁面上顯示的分數是兩次的平均（向下取整）。
4. **結構化**（`structure.md`）：和評分同時進行。給出分類和標籤（頁面上顯示的就是這一份）、主體公司，判斷這篇是一條具體新聞、講多件事的綜合稿，還是材料不夠、說不清；是具體新聞的，抽出它的事實（誰、做了什麼、對什麼、什麼時候）和原文裡的出處、前提條件。主題頁、事件歸組和日報都靠它。
5. **寫標題摘要**：等結構化完成再寫。入選的和差一點入選的（平均分高於 `understandFloor`），按 `content-understanding.md` 寫中文標題、答案先行的摘要和推薦理由；其餘的按 `summarize-*.md` 寫簡短的標題摘要，進“全部動態”。瀏覽“全部動態”（網頁列表，介面、給 Agent 的最新列表和 MCP 的全部模式，“全部動態”RSS）只出平均分不低於 `browseFloor` 的資料，沒評上分的照常出；帶搜尋詞時仍搜全部。X 帖子沒有正文或只含連結時，保留原帖的連結、圖片和引用，不呼叫寫作或翻譯模型，也不生成“請補充正文”的文案；已經取得實際正文的 X 長文照常處理。寫好的文字用了 `industry/wording.ts` 裡列出的詞時，再讓模型只改這些詞一次（`mend-wording.md`）。
6. **歸組與去重**（`group-*.md`）：不同來源報道的同一件事歸成一個事件，事件頁有綜述（`story-digest.md`），“熱門”按事件排。修改綜述提示詞前，可用 [綜述評測](story-digest-evaluation.md) 在同一批事件上把現有提示詞和候選提示詞並排比較。分數夠了的資料要等歸組完成才進精選：模型同時判斷它和精選裡已有的報道是不是同一條新聞，以及它有沒有精選還沒給過的具體資訊。
   - 同一條新聞的幾篇報道都可以入選：網頁上折成一個閱讀組；API、RSS 和同步介面每條新聞只出一條，由代表報道出面：官方一手優先；其次是核實過的官方賬號（填了 `publisherRole` 和 `owner_entity_id` 的 `T1_5` 賬號，新聞的主體正是這家公司，機構先於個人）；再往後是有全文的、分數高的、發得早的。
   - 不是同一條新聞、但沒有新資訊的（換個說法再介紹一遍已經披露的能力、只是上架到別的平台、只重複已選要點的彙總），不進精選，留在“全部動態”。講多件事的綜合稿不單獨成事件，只掛到它提到的事件上，有精選沒覆蓋的重要內容才入選；材料不夠、確認不了是哪條新聞的，不進精選。
   - 顯式撤回的報道保留歷史歸屬，但不再參與之後的歸組召回、候選代表、事件起點或自動事件比較；同網址及 X 回覆／引用也不能借它提供身份依據。同一事實仍有有效報道時使用有效稿，全撤回則暫不召回；恢復公開後可重新參與。只展示摘要或尚未釋出的記錄不等於撤回，保留原有資格。已有關係和判斷不刪除，不批次重新歸組。
   - 確認之前資料只在“全部動態”裡，等得再久也不會自動放行。模型呼叫失敗或回答不合格式，這條資料就停在那裡：等待超過 10 分鐘會告警，後臺“執行”頁列出這些資料，可以在後臺“內容診斷”裡開啟這條資料，點“重新歸組”。所以歸組用的模型要能穩定按格式回答。
7. **日報、週報、月報**：
   - **日報**每天 08:00 出（日報、週報、月報的出刊時間在 `site/site.ts` 的 `EDITION_TIMES`，下面按預設值寫），覆蓋前一天 08:00 到當天 08:00，按規則編排，不呼叫模型。一件事一條，取報道最多的那條新聞裡最權威的一篇，同一事件當天的其他進展列在下面，講多件事的綜合稿掛到它提到的最重要那件事下面。最近 7 期報過的不再出現；報過的事件再有進展，只有當事方自己有新動作（教程、觀點這類 `commentary` 類別不算）、或這條進展有 4 家以上信源報道時才進正文，其餘進快訊。沒有報道入選、但有官方原帖並且已有 3 個以上獨立參與方的事件也會補進來（只進日報，不進精選、不推送）。按重要性排序（入選報道的最高分、當天討論它的獨立參與方、有沒有官方原帖，跟進的減分），前 12 條進正文，同一信源最多 2 條，再往後最多 10 條一行快訊。第一條是頭條，導語就是它自己的標題和摘要；第 2–4 條是今日看點。
   - **週報**（每週一 10:00）和**月報**（每月 1 日 10:30）由這一週、這個月的日報彙編：同一事件跨天只算一件，按日報給它的位置（頭條、看點、上了幾天）、報道面和評分排序，週報取前 20 件、月報取前 30 件，按日報的分節分欄目。模型（`report-period.md`、`report-period-sections.md`）只寫總述和三件以上欄目的一句導讀，不增刪條目；它寫出了條目裡沒有的名字或數字（拉丁字母的名稱、三位以上或帶小數點、百分號的數字、詞表裡的公司），這段話就不用：總述換成按模板生成的一句，欄目不放導讀。行業通用詞（`taxonomy.ts` 的 `PLAIN_TERMS`）和站名不受這個限制。
   - 每條精選只進一期：按它的時間算，確認入選比它晚的按確認時間；截止以後才確認的進下一期。
   - 每半小時檢查一次：到點的刊期出一次，已經出過的不重寫；停機錯過的、失敗的，在之後的檢查裡補上。日報時段裡有資料經過判斷、但沒有新事件時照常出空刊；沒有任何資料經過判斷仍算失敗，缺期按[部署說明](deploy.md#更新)告警。週報、月報的週期內，應有日報齊全且原始正文條目全部為空時，自動跳過該期，不寫空週報或月報、不呼叫模型，也不記為生成或失敗；首個週期從全站最早日報開始檢查。沒有可彙總條目時，若缺失日報或原有條目後來無法公開，仍保留原有錯誤。跳過不寫永久標記，在現有補刊範圍內更正日報後可重新生成。

每一步的提示詞都在 `industry/prompts/`，改提示詞不用改程式碼。提示詞的版本就是它內容的雜湊：改了提示詞，之後的新資料按新版判斷，已經判過的不會重算。

## 門檻：`industry/selection.ts`

```ts
export const SELECTION = {
  thresholds: { T1: 60, T1_5: 65, T2: 76 },   // 兩次評分的平均至少要到這個數
  classes: {                                  // 信源類別：這類信源的門檻不低於這裡的數
    ecosystem: { label: "生態與基礎設施", threshold: 70 },
    leaderboard: { label: "評測榜單", threshold: 76 },
  },
  understandFloor: 50,                        // 平均分高於它的未入選資料，也按入選的寫法寫
  browseFloor: 40,                            // 瀏覽“全部動態”只出平均分不低於它的資料，搜尋不受限
};
```

官方一手信源（T1）門檻低一些，媒體和個人（T2）門檻高一些：同樣一件事，官方原文更值得先看。沒有門檻的分級（`EXCLUDE_MP`）不參與精選。

分級只說明來源是不是官方、一手。有些官方信源的日常內容主要寫給開發者或業內（晶片與雲服務、開發框架與工具鏈、評測榜單……），讀者要看的只是其中的大事：在後臺“信源”頁給它選一個類別，門檻抬到不低於類別的數。只抬不降，分級門檻本來就更高的不受影響；不選類別就只按分級。類別的鍵存在信源上，上線後不要改名，改了的類別會悄悄失效；評測樣本不帶類別，按分級門檻算。

`browseFloor` 設成 `0` 就和以前一樣，“全部動態”列出全部公開資料。

這組數是 AIHOT 在 AI 領域一直在用的門檻，偏嚴：寧可少選幾條，也不讓噪聲進精選。換了行業、改了評分標準，一定要按下面的辦法重新校準。

## 校準

### 1. 準備樣本集

從你自己的信源裡挑 100–200 條資料，一條一條標“該選 / 不該選”，存成 `.data/gold.jsonl`（`.data/` 不進 Git）。每行一條：

```json
{"caseId":"law-001","material":{"title":"原文標題","originalTitle":null,"publishedAt":"2026-10-01T09:00:00+08:00","sourceName":"信源名稱","bodyZh":null,"bodyOriginal":"正文……"},"sourceFacts":{"sourceKind":"rss","sourceTier":"T1","firstParty":true,"language":"zh"},"samplingContext":{"benchmarkSplit":"development","samplingStratum":"regulation"},"gold":{"decision":"select"}}
```

| 欄位 | 說明 |
|---|---|
| `caseId` | 唯一編號 |
| `material` | 標題、原標題、釋出時間、信源名、正文（中文正文放 `bodyZh`，原文放 `bodyOriginal`，有一個就行） |
| `sourceFacts` | 信源型別、分級、是否一手（線上只有 `T1` 算一手，標註時保持一致）、語言。分級決定用哪個門檻 |
| `samplingContext` | 可選。`benchmarkSplit` 分開發集和留出集，`samplingStratum` 是你自己的分組（比如“新規”“判決”“營銷”），看錯在哪一類 |
| `gold.decision` | `select` 該選，`reject` 不該選，`either` 兩可（不計入準確率） |

`industry/gold.example.jsonl` 有兩條示例。

幾條建議：

- 多放**難例**：差一點就該選、差一點就不該選的。一眼就能判斷的放太多，準確率會虛高。
- 分出一部分做**留出集**（`benchmarkSplit: "holdout"`），調提示詞只看開發集，最後再用留出集檢查一遍，免得把提示詞調成只會做這幾道題。
- 標註的人最好就是以後讀這個站的人，或者和他們口味一致的人。
- 評測只跑預篩和兩次評分，不含第 6 步的去重：按這條資料本身該不該選來標，不要因為同一件事已經選過另一篇就標“不該選”。

### 2. 跑評測

```bash
node --env-file=.env scripts/eval-selection.ts --gold .data/gold.jsonl --split development --label "第一版評分標準"
```

對每條樣本跑一遍預篩和兩次評分，輸出：

- **有效輸出準確率、查準率、查全率和 F1**：只看成功得到入選決定的非 `either` 樣本，用來判斷模型答出來以後有多準；
- **覆蓋率**：成功得到入選決定的樣本佔全部非 `either` 金標樣本的比例；**完整準確率**則用全部非 `either` 金標樣本作分母，把模型失敗或回答不合格式也算作沒有正確完成；
- `either` 始終不進入上述質量指標的分母；報告另外記錄決定樣本失敗數與 `either` 失敗數。`goldSelectRate` 按全部非 `either` 金標計算，因此同一批樣本在不同模型間應保持一致；
- 門檻從 40 到 90 每隔 2 分（範圍可以在下面說的 `DEPLOYMENT.selectionGold` 裡改），各自會得到什麼結果；門檻掃描同樣同時報告有效輸出準確率、覆蓋率和完整準確率；
- 判錯的條目，完整報告寫到 `.data/eval/`，同時匯入後臺 SelectBench（加 `--no-import` 不匯入）。

不傳 `--models` 時，評測用“精選評分”這一步線上正在用的模型：後臺“模型與評測”頁切換過的優先，其次是環境變數 `SCORE_MODEL`，再其次是 `site/models.ts` 的 `DEFAULTS.score`，都沒有就用預設模型（`.env` 裡的 `LLM_*`）。`--models default,deepseek-flash` 可以在同一批樣本上比較幾個模型。其他常用引數：`--n 200` 最多抽多少條，`--split holdout` 只跑留出集，`--no-import` 不匯入 SelectBench。在 `site/site.ts` 的 `DEPLOYMENT.selectionGold` 裡寫好樣本檔案、抽樣條數、只抽哪一份和門檻掃描範圍，以後不帶引數執行就用這一套。

同一次評測裡，不同樣本渲染出完全相同的評分輸入時，只共享模型的評分結果，各樣本仍按自己的預篩結果、信源分級門檻和標註獨立計分；失敗的結果也在這次執行裡共享，這樣第一次跑和用已有結果重跑覆蓋的樣本一樣。重複執行會複用已有回執。報告裡的 token 用量和平均耗時，按相關回執的全部請求嘗試彙總，解析失敗後的重試也算在內；用已有結果重跑時，顯示的是這些回執累計的用量，不代表這次新增的費用。

### 3. 看錯例，改標準，再跑

在後臺 SelectBench 裡逐條看判錯的資料和模型給的理由：

上傳多模型報告時，同一 `caseId` 在各模型下須使用相同的 `gold` 標註，模型的 `decision` 可以不同。標註衝突的報告會在寫入前被拒絕，避免同一條資料在並排比較時出現不同的人工答案；不提供逐例 `cases` 的報告仍可匯入。

- 該選沒選上，多半是評分標準裡沒說清它為什麼重要：在 `selection-score.md` 裡把這類價值寫進“必須正常評價”的部分，給出例子。
- 不該選卻選上了，多半是噪聲沒壓住：寫進“必須壓住”的部分。
- 整體偏松或偏緊，而判錯的條目分數都貼著門檻，再調 `industry/selection.ts` 的門檻。

先改標準，再動門檻：門檻只能整體移動，解決不了“哪一類判錯了”。每改一次跑一遍，SelectBench 裡能看到每一版的對比。比較模型時不要只看有效輸出 F1：如果覆蓋率明顯不同，還要一起看完整準確率；高分但經常無法完成結構化判斷的模型，不應被失敗樣本從分母裡“隱藏”掉。

## 換模型

後臺“模型與評測”頁能看到每一步當前用哪個模型、近期的成功率、耗時和 token 用量，也能直接切換（隻影響之後的新任務）。換評分模型之前，先用 `--models` 在同一批樣本上比一比。
